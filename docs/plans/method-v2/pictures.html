2 · Where you are needed, and the ladder

Everything else is done for you. Your eight touchpoints, what only you can give, and how a stuck problem climbs.

Your eight touchpoints

1
Free talk. Goal, why, what you like in other apps. State the goal and the constraint; let the AI propose the solution.
as long as it takes
2
Correct "what I heard". Five lines after every talk round.
2 minutes
3
Choose in the plan. Time per part, the faster way, must / nice / later.
10 minutes per phase
4
Answer the main questionnaire in one go. "Explain again" is always allowed.
one sitting
5
Sign the confirm sheet the same day, so builders never idle.
same day
6
Test by scenario on the PC preview when a feature is complete.
10–20 minutes
7
File bugs from any device: saw, expected, screenshot. Or say it in chat and it is filed for you.
30 seconds each
8
Say yes to switch ON, and read the phase numbers with Fable.
per release / phase

What only you can give

  • Real material: your own notebooks, summaries, words. Tests on real values catch real bugs.
  • Screenshots of apps that do it the way you like. One picture beats a page.
  • Must-never lines. Each one becomes a test.
  • Device facts for a bug: where, which app, what you tapped, what you saw, in order.
  • Overrides said plainly: "I hear the reason, I choose X anyway." Logged as an override.
  • New ideas go to the ideas list, never into a running part.

The ladder: who takes a stuck problem

Sonnet
medium effort
Builds one task. Three fails on the same thing, each try with new evidence (a failing test, a trace, a measurement).
↓
Opus
medium effort
Takes the task over. Manages the build and reviews once.
↓
Opus
high effort
New (owner, 21 Nov): if the result falls short, raise the effort before changing the model. Smaller step, about a third more cost.
↓
Fable
medium effort
Plans each phase with you; otherwise only for what Opus could not solve and for very risky decisions. Used as little as possible.
↓
You
Last. Only for money, logins, switching ON, data loss, a device test, or a real product decision.

Honesty rules (owner, 21 Nov)

  • Every pick carries the case against it, in one line.
  • A position changes only for a named new reason: new evidence or a new argument.
  • Override log: "owner chose X; the AI's reason against was Y".
  • "Done" needs proof: the test run, the screenshot, the page in a browser.
  • Tells to watch: praise of your idea, instant flips, "works" without proof.
Rules change only between phases, with your word.Learning Notes · method v2 · 21 Nov 2026

3 · One source, two faces, and where your old files go

The repo is the only source. A free program rebuilds every face on each push. No AI, no tokens, nothing to keep in sync by hand.

Source · the repo on GitHub

  • Constitution: CLAUDE.md + rules/ (+ Spec Kit points here)
  • Method: this flow, one page
  • Phase plan: the one live plan
  • Specs: features/ (template v2) and parts/ (shared part cards)
  • Decisions log with the override log
  • Changelog
  • State: one file: now, needs you, next
  • Ideas (parking lot) · Metrics (numbers)
  • GitHub Issues: every bug and finding; the issue number is the bug id
→

GitHub Action · on every push

  • Reads spec statuses, part cards, issues
  • Runs analyze: rules ↔ scenarios ↔ tests ↔ tasks, shared parts really used
  • Writes one data file (specs, bugs, states)
  • Builds and publishes the site
  • Free. No AI. No secret needed on GitHub Pages.
→

Faces · what you open

  • Site (GitHub Pages): spec pages with pictures and status badges, the confirm sheet read-only, the bug board (pending · working on it · complete, one tap to detail), decisions, changelog, state. iPad, phone, PC.
  • In-app "Project" notebook (later, when database views exist): the same data file inside Learning Notes. Your app shows your bugs.
  • Chat: status line morning and evening; build report by scenario per feature; "what I heard" after each talk.
