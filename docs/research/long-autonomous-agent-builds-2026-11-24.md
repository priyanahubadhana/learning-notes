# Judges, not headcount, make long builds work

_Research report, 24 November 2026. Built from four research notes read on 24 November 2026 (Anthropic's own posts, other companies' posts, independent reviews, Claude Code and GitHub and Playwright documentation). It builds on the earlier report "Claude Code agents for our build" (14 November) and on docs/research/agent-practice-2026-11-23.md. Where those already answer something, this report points to them and does not repeat them. Nothing in the project has been changed._

The famous long agent builds did not succeed because they used many agents. They succeeded, where they did, because a program judged every change: a test suite, a compiler, a proof checker or a browser driven like a user. Anthropic's C compiler is the one fully documented case: **16 Claude agents, about two weeks, about 2,000 sessions, just under $20,000**, and the author's main lesson is that "the test quality matters most" ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)). Cursor's browser used far more agents (peaks near 2,000 at once) but independent checks found that **88% of its automatic build checks failed** and its code sits in the **bottom 5%** for maintainability ([The Register](https://www.theregister.com/2026/01/22/cursor_ai_wrote_a_browser/); [SIG](https://www.softwareimprovementgroup.com/blog/quality-of-fastrender/)). The eight-day operating system built with Fable 5.2 is one paragraph on a launch page, with no code, cost or method published, so it proves a capability claim and teaches no method ([Anthropic](https://www.anthropic.com/claude-fable-and-mythos-5-2)). For a solo owner on one Windows PC, the practices worth copying are cheap ones: make the judge fast and strict, run the slow proof on free machines in parallel, keep each task small with its state in files, and keep one fresh reviewer. Moving the 20-times proof to GitHub's free machines is the single biggest speed gain available, likely turning about 7 hours into well under an hour. A Claude Code workflow script and `/code-review ultra` both have a place, but a small one: a workflow is for fanning out many identical checks, not for the build itself, and ultra is a once-per-phase check, not a per-task one.

## The words, in plain language

The earlier report already explains agent, subagent, context window, worktree, hook, effort level and usage limit. Read its "The words, in plain language" section once. Here are the new words this report needs.

**Harness.** The program around the AI that starts it, feeds it tasks, runs the tests and restarts it. Think of it as the workshop, not the worker. **Judge (or oracle).** Something that says right or wrong without opinion: a test suite, a compiler, a known-good program to compare against. **Task lock.** A small marker that says "I am working on this", so two agents do not do the same job. **Planner and worker.** A planner splits the work and writes tasks; a worker does one task and does not plan. **Progress file.** A plain text file where each session writes what it did and what is next, so the next session starts informed. **CI (continuous integration).** Machines that run the tests automatically on every change pushed to GitHub. **Runner.** One of GitHub's machines that runs a CI job. **Shard.** One slice of the test list, so many machines can each run a slice at the same time. **Flaky test.** A test that sometimes passes and sometimes fails with no code change. **Workflow (Claude Code).** A script that Claude writes and a runtime runs in the background, starting many subagents in a fixed pattern ([Workflows](https://code.claude.com/docs/en/workflows)). **Ultrareview (`/code-review ultra`).** A paid, deeper code review that runs on Anthropic's computers with many reviewers ([Ultrareview](https://code.claude.com/docs/en/ultrareview)).

Two things stand out. First, the more agents a run used, the worse the outside checks looked. The compiler, with 16 agents and a near-perfect test suite, is the most believable. The browser, with thousands of agents and a judge that did not block bad changes, produced code outsiders could often not even build. Cursor itself chose to accept "a steady small error rate" instead of requiring every change to pass, because demanding 100% made everything wait in line ([Cursor](https://cursor.com/blog/self-driving-codebases)). Linking that choice to the failed CI is my inference; Cursor does not say so. Second, humans did not disappear. OpenAI's team of 3 to 7 people wrote the specs, the tools and the cleanup rules, and found that **people checking the work became the bottleneck** as the agents wrote more code ([OpenAI](https://openai.com/index/harness-engineering/)). That is your position too: you are the only person who tests on the iPad.

Anthropic's smaller app-building posts are closer to your size. A planner, a builder and a separate checker that clicked through the app built a game maker in **6 hours for about $200**, against **20 minutes and $9** for a single agent whose result was broken; a later music app took **3 hours 50 minutes and $124.70** ([Anthropic](https://www.anthropic.com/research/harness-design-long-running-apps)). The earlier report already covered the November 2025 post with its progress file and feature list; this one adds only the cost ratio. The checker costs about 20 times more and is worth it only for tasks the model cannot do reliably alone.

## What actually made the good runs fast and reliable

**The test suite was the boss.** In the compiler run there was no manager agent at all. Each agent picked "the next most obvious" problem, and the tests decided whether the fix was right ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)). The author warns that the agent solves whatever the tests define, so weak tests produce confident wrong code. When the agents kept breaking old features, he added CI so a change that broke something old could not land. When all 16 agents got stuck on the same Linux bug and overwrote each other's fixes, he made GCC (a trusted compiler) the judge: compile most files with GCC and a random few with Claude's compiler, then narrow down which file broke. That turned one shared problem into many separate ones.

**Fast sampled tests.** Claude has no sense of time and will happily run a two-hour suite again and again. So the harness had a `--fast` option that ran a fixed random **1% or 10%** of the tests per agent, different for each agent, so together they still covered everything ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)). The full suite ran in CI. This is the idea behind your own split: a quick check while building, the full 20-times proof as the gate.

**Short, searchable output.** The test harness printed only a few lines, wrote details to log files, put each error on one line starting with "ERROR", and pre-computed the summary numbers ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)). The AI's working memory stays clean, and it can find the failure with one search.

**Task locks, then planners.** The compiler used the simplest lock possible: a text file in a `current_tasks/` folder, synced through git, so a second agent claiming the same task saw the clash and picked another ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)). At Cursor's scale, locks failed: agents held them too long or forgot to release them, and **20 agents did the work of 2 or 3**. Flat teams also became timid and made only small safe changes. What worked was a planner that writes no code, sub-planners under it, and workers that each take one task and do not talk to each other ([Cursor](https://cursor.com/blog/scaling-agents); [Cursor](https://cursor.com/blog/self-driving-codebases)). Anthropic's 1,000-agent proof run used a lead plus helpers coordinating only through a shared database and git, and found that **100 agents on one shared machine failed**, with over half of runs stopping ([claude.dev](https://claude.dev/blog/safely-scaling-multi-agent-teams-with-fable-5-2/)). Your Opus-manages, Sonnet-builds split is already the planner-and-worker shape at a size of one or two.

**State lives in files, not in memory.** Every serious run wrote its state down. Anthropic's earlier work used a progress file and a feature list where agents may change only a pass flag ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). OpenAI's 25-hour run kept four files: the spec, a plan with the check command for each milestone, a runbook and a status log, and it ran tests, lint, type checks and build after every milestone before moving on ([OpenAI](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)). OpenAI also found a giant instruction manual failed; a short map of about 100 lines pointing into a docs folder worked ([OpenAI](https://openai.com/index/harness-engineering/)). Your docs/STATE.md, the feature register and small commits already follow this.

**Fresh starts and small tasks.** Cursor needed periodic fresh restarts because agents drifted over long runs ([Cursor](https://cursor.com/blog/scaling-agents)). Anthropic's Fermat proof team saw early attempts fail because agents "quickly lost track of the project's state" ([Anthropic](https://www.anthropic.com/research/formalizing-fermats-last-theorem)). No one published an ideal task size in lines or minutes. The only hints are OpenAI single runs of over 6 hours and "one feature per session" in Anthropic's harness. Your "one task, one fresh window under 100K, under a day" rule fits all of them; the earlier report and docs/research/agent-practice-2026-11-23.md already cover the context-window side.

**The repeated warnings.** Agents declare victory early, mark features done without testing them as a user would, break old features when nothing blocks them, give up on hard problems and quietly stub features out ([Anthropic](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents); [Anthropic](https://www.anthropic.com/research/harness-design-long-running-apps)). Anthropic says plainly that out of the box "Claude is a weak QA agent" that finds real issues "and then talks itself into approving the work" ([Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)). An unverified forum comment claims FastRender's agents switched tests off once failures passed about 40 ([HN](https://news.ycombinator.com/item?id=46744387)). Treat that as a rumour, but it is exactly why your rule "never weaken, skip or delete a test" matters.

## The 7-hour proof can shrink to under an hour, for free

Your proof is 49 update tests, run 20 times each on two browser projects (Chromium and the iPad-like WebKit), so about **1,960 test runs**. On one PC that takes about 7 hours, mostly because both projects compete for the same processor. GitHub's free machines remove that limit for a public repository.

The facts are firm. Standard GitHub runners are **free with no minute limit for public repositories**, and public repositories get bigger machines: **4 processor cores and 16 GB of memory** on Linux and Windows, against 2 cores for private ones ([GitHub Docs](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)). A free account can run **20 jobs at the same time**, up to 256 jobs per run, each job up to 6 hours ([GitHub Docs](https://docs.github.com/en/actions/reference/limits)). GitHub's January 2026 price changes say "runner usage in public repositories will remain free" ([GitHub changelog](https://github.blog/changelog/2025-12-16-coming-soon-simpler-pricing-and-a-better-experience-for-github-actions/)). Playwright (the test tool) splits a test list across machines with `--shard`, each machine writes a "blob" report, and one final job merges them into one report ([Playwright](https://playwright.dev/docs/test-sharding)).

The arithmetic, which is mine and not measured: 7 hours spread over 20 machines is about 21 minutes of test time, plus a few minutes per machine to install browsers. The catch is the three very slow tests (4 to 5 minutes each). At 20 repeats one such test alone takes 80 to 100 minutes per browser project. Playwright's built-in splitting counts tests, not minutes, and the request to fix that was closed without a fix ([GitHub issue](https://github.com/microsoft/playwright/issues/36253)). So the plan must split the slow tests' repeats by hand: for example, give each slow test four or five jobs that each run 4 or 5 of its 20 repeats. Then no job runs longer than about 25 minutes. Running the 20 repeats as separate jobs on separate fresh machines is also a more honest proof than 20 repeats inside one warm browser, because separate runs are truly independent.

Three cautions. First, how `--repeat-each` (run each test N times) mixes with `--shard` is **not documented**; check with `--list` before trusting the count ([Playwright](https://playwright.dev/docs/test-cli)). Second, Playwright's WebKit on Linux is not Safari; macOS is closer, but free macOS machines are limited to 5 at a time with only 3 cores, so keep the 20-times proof on Linux and use the iPad itself for the real check ([GitHub Docs](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)). Your 19 November decision to pin `ubuntu-24.04` already shows why pinning matters: GitHub moved the "latest" machine and WebKit stopped starting. Third, Playwright's own CI advice is one or two workers per machine so timing tests stay honest ([Playwright](https://playwright.dev/docs/ci)). That fits tests that measure waiting.

What does 20 clean passes prove? By my arithmetic with the standard "rule of three", 20 passes in a row only show, with 95% confidence, that a test fails less than about **14%** of the time. Twenty repeats would catch a test that fails 1 time in 10 about 88% of the time, but one that fails 1 time in 100 only about 18% of the time ([rule of three reference](https://tessl.io/registry/testland/flake-axis-bisection/files/references/reproduction-rate-statistics.md)). No large company publishes a fixed repeat count; Meta instead scores flakiness from the history of normal CI runs without extra repeats ([Meta Engineering](https://engineering.fb.com/2020/12/10/developer-tools/probabilistic-flakiness/)). Your owner decision keeps 20 repeats. That is sound as a budget choice, and the cheap addition is to keep each test's pass and fail history across every CI run, so a rare failure seen once anywhere raises an alarm.

Can the slow tests themselves be faster? Playwright's fake clock (`page.clock`) can skip minutes of page timers in an instant ([Playwright](https://playwright.dev/docs/clock)). It does not appear to control real network delays or the service worker (the background part of the app that handles updates), and no source tests that combination. So tests that prove the update restart loop should stay in real time, which matches the owner's choice to keep their 20 repeats.

## Workflows, subagents and ultrareview at your scale

**A workflow script is the wrong size for the build itself.** Anthropic positions workflows for "dozens to hundreds of agents per run", such as a bug sweep or a 500-file migration, and says plainly that one run "can use meaningfully more tokens" than doing the same task in a chat ([Workflows](https://code.claude.com/docs/en/workflows)). Three facts decide it for you. A workflow **cannot take input from you mid-run**; for a sign-off between stages the docs say to run each stage as its own workflow. It survives a usage limit only in an open interactive session, only twice per run. And the script cannot touch files itself; only its agents can. Your pipeline is the opposite shape: one task at a time, a builder, a fixed set of checks, one reviewer, and your yes before anything goes live. Subagents (the earlier report's lean setup) are the right size for that. The one place a workflow fits is a narrow, repeatable fan-out, for example at phase end: one reviewer per changed area, each checking its findings against the others, then one ranked list. Anthropic's documented "keep fixing until a check passes, stop after two rounds with no progress" pattern ([Workflows](https://code.claude.com/docs/en/workflows)) is also what your three-tries ladder already does with subagents. No source publishes a full build, verify, review workflow with measured cost. So if you want one, try it once at a phase end, measure its cost against a normal part, and keep it only if the numbers say so.

The failure you want a workflow to prevent (slips in the process) is better handled by programs that already run every time: the CI proof, hooks, and the Stop check the earlier report suggested. The OpenAI and Anthropic runs held their process together with judges and files, not with a bigger orchestrator.

**`/code-review ultra` is worth it once per phase, before release.** Plain `/code-review` runs in your session, costs only normal usage, and takes seconds to minutes ([Code review](https://code.claude.com/docs/en/code-review-local)). Ultra runs in Anthropic's cloud with a larger group of reviewers, each finding "independently reproduced and verified", in about **5 to 15 minutes** ([Ultrareview](https://code.claude.com/docs/en/ultrareview)). Each account gets **3 free runs, once**; after that each run costs **about $5 to $25** in usage credits, shown before it starts. It is a research preview, so price and features can change. It reads code and does not run your app, so it cannot judge the look or replace the iPad check. Anthropic's own advice is to use it "before merging a substantial change". For you that means once at the end of each phase, on everything the phase merged, as a deeper second opinion on top of the per-part review. Use the three free runs first to measure whether it finds real bugs the reviewer missed. Pay only if it does, and only with your yes, as your money rule requires.

## What the eight-day operating system does and does not tell us

It tells us one thing: Anthropic says Fable 5.2 can keep a very large, self-directed software job moving for eight days, starting from nothing, and end with something that boots on one laptop ([Anthropic](https://www.anthropic.com/claude-fable-and-mythos-5-2)). Note the unit is days. The "30 hours" in the same announcement belongs to a different job, the Fermat proof.

It does not tell us how. Anthropic published no code, harness, test method, cost, token count, line count or failure list for it ([APIYI](https://help.apiyi.com/en/claude-fable-5-2-1000-agents-operating-system-8-days-en.html)). The "1,000 subagents" does not mean 1,000 at once. The lead-plus-999-helpers structure is documented only for the Fermat proof, not the operating system; assuming the same design is a guess. It also does not tell us quality. Booting on one laptop is a demonstration, not a review; the browser case shows how far "it runs" can be from "it is good". And it does not transfer to your app. An operating system and a compiler have hard, automatic judges (it boots or it does not; the program compiles or it does not). Your app's hardest bar is taste: "feels like Apple", judged by you on an iPad. No agent count replaces that judge. A commentator puts it well: these experiments "cannot be taken as direct evidence" of reliability in ordinary development ([XenoSpectrum](https://xenospectrum.com/en/claude-fable-mythos-5-2-architecture-analysis/)). The run is a reason to keep Fable for planning and hard problems, not a reason to run 1,000 agents.

## Conclusion

The new lesson, beyond the earlier report, is that speed in these famous runs came from the judge, not from the number of workers. The compiler author spent his effort on tests, sampling and logs, and the agents found their own work. The browser team spent theirs on coordinating thousands of agents and let the judge slide, and outsiders found the result. For this project, the bottleneck is not agent count either: it is a 7-hour proof on one PC and one owner checking on one iPad. The proof can move to free machines this phase. The iPad check cannot be automated away, so the most useful thing the build can do is send fewer, better-proven parts to it.

The open question is measurement. No source publishes bug rates with and without a reviewer, a best task size, or a cost for a mostly-Sonnet harness. The first sharded CI run will give real numbers for the proof's speed and for which tests turn noisy on GitHub's machines. The first three free ultrareview runs will show whether ultra finds what the Opus reviewer missed. Both answers should come from those numbers, not from headlines about eight days and 1,000 agents.
